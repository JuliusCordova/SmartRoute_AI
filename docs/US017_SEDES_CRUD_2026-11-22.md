# SmartRoute AI — US-017: CRUD de sedes / centros de distribución

**Fecha:** 22 de noviembre de 2026. **Estado:** implementación de código; no desplegado en GCP. Validación de UI real y capturas pendientes.

## Necesidad y alcance

El usuario OPERATOR administra un catálogo permanente de **sedes o centros de distribución** en la base Firestore nombrada `smartroute`. Cada sede tiene:
- `id` UUID generado por servidor, `code` único e inmutable, `name` y `address_label`.
- `geo` (latitud y longitud del área piloto de Lima), `location_precision` y confirmación obligatoria para geocodificación aproximada.
- `active` (true/false), `version` para concurrencia optimista, `created_at`, `updated_at`, `created_by`.

El operador puede crear, listar, consultar por ID, editar nombre/dirección/coordenadas y **desactivar sin eliminar físicamente**. La desactivación conserva la reserva del código único y el histórico de rutas.

## Contratos HTTP implementados

| Verbo | Endpoint | Descripción | Permiso |
| --- | --- | --- | --- |
| POST | `/api/v1/distribution-centers` | Crear sede | OPERATOR |
| GET | `/api/v1/distribution-centers?limit=50&cursor=...` | Listar sedes paginadas | OPERATOR |
| GET | `/api/v1/distribution-centers/{center_id}` | Consultar sede | OPERATOR |
| PUT | `/api/v1/distribution-centers/{center_id}` | Actualizar con `expected_version` | OPERATOR |
| DELETE | `/api/v1/distribution-centers/{center_id}` | Desactivar (soft delete) con `expected_version` | OPERATOR |

La UI reutiliza `GET /api/v1/geocoding/autocomplete` para elegir la dirección. **No** envía ni almacena una clave de Geoapify en el navegador. Se mantiene la validación Firebase en Gateway y Backend y el token IAM servidor→servidor.

### Persistencia y relación con rutas

- Colecciones nuevas: `distribution_centers/{id}` y `distribution_center_codes/{CODE}` (índice único permanente).
- `POST /api/v1/optimized-routes` admite `distribution_center_id` opcional; al guardarlo, el Backend verifica en Firestore que la sede exista, esté activa, corresponda con `depot` y no haya cambiado durante la transacción.
- Cada ruta nueva guarda `distribution_center_id`, `distribution_center_name` (snapshot de nombre), y la coordenada `depot` persistida como antes. Las rutas antiguas siguen funcionando sin `distribution_center_id`.
- El valor `depot` del contrato se mantiene por retrocompatibilidad aunque la interfaz muestra **Centro de distribución**.
- Si se desactiva o modifica una sede, una ruta histórica no cambia: la referencia es informativa y el snapshot permanece intacto.
- No se borra `distribution_centers` físicamente desde este CRUD. La versión concurrente provoca HTTP 409.

## Flujo de UI

1. Ingresar como OPERATOR al Centro de Control y abrir la sección **Centro de distribución**.
2. Consultar el catálogo. Buscar por nombre, código o dirección.
3. Elegir una sede **activa** como origen de las nuevas rutas.
4. Para crear, pulsar **Nueva sede**; introducir código y nombre, buscar la dirección, seleccionar sugerencia y confirmar si la geocodificación es aproximada, luego guardar.
5. Para editar, seleccionar **Editar**, corregir campos y guardar usando versión actual; el código permanece inmutable.
6. Para desactivar, seleccionar **Desactivar**, confirmar y verificar que ya no pueda elegirse para planificar.

## Seguridad y riesgos

- Firestore usa `firestore_client()` (selección fail-closed) y base `smartroute`; nunca `(default)` o `gestioncitas`.
- Gateway permite **solo** endpoints CRUD específicos y UUIDs, verificación de token Firebase y lista exacta CORS.
- Edición exige `expected_version`; el código es único y no cambia; no hay borrado irreversible de sedes.
- **QA:** no crear sedes reales de clientes ni promover revisión hasta pasar el gate de test e integración en Cloud Run etiquetada `--no-traffic`.
